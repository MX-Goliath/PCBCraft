# Архитектура

`eda-app → eda-render / eda-io / eda-core → eda-geom`

- `eda-geom`: координаты документа в целых нанометрах.
- `eda-core`: Document, Pad, Track, Layer, Units, Schematic, валидация, история.
- `eda-io`: собственный JSON v1, ограничение размера, проверка данных,
  запись через временный файл в том же каталоге и atomic persist.
- `eda-render`: camera, read-only canvas, hit testing и view state.
- `eda-app`: eframe/wgpu, оболочка, общие обработчики команд для
  меню/toolbar/shortcut, диалоги, Properties, настройки.

Ядро не зависит от egui, Win32 или Altium. UI отправляет изменения через
History::commit. Пока история хранит снимки малых документов; далее заменить
на типизированные изменения, сохраняя семантику атомарности и ревизий.

eframe 0.32.3 и egui 0.32.3 зафиксированы совместно. Используется один
цикл событий и wgpu backend eframe; отдельный GPU device не создаётся.
Canvas пока использует egui Painter, следующий этап добавит собственные
пакеты отрисовки через тот же backend. egui_dock будет подключён при
реализации docking; текущие панели поддерживают resize/hide.
Messages и Properties разделяют одну правую область с нижними вкладками;
это собственная компоновка на egui panels, ещё не полный docking.

Визуальная цель — точная копия Altium 24.4.1 согласно пользовательскому
уточнению. Собственная модель и формат не дают оснований менять привычную
компоновку интерфейса. Текущие расхождения: docs/interface/visual-parity.md.

Вкладки хранят независимые камеры, выделение и историю. Сохранённый снимок
определяет dirty state, поэтому undo к сохранённому содержимому снимает `*`.
Настройки и геометрия панелей сохраняются eframe; документы и несохранённая
сессия пока не восстанавливаются автоматически.

`eda-io::altium` читает проект INI и схему CFB/ASCII. Модель Schematic хранит
типизированную сцену, компоненты, исходные записи и архив оригинала.
Парсер не зависит от GUI/Win32. Представление хранит независимые фильтры
выбора компонентов, проводов, текста и графики. Рендерер читает документ;
выбор и изменения масштаба не меняют импортированные данные.
CFB, кодировки и zlib обрабатываются переносимыми Rust-библиотеками.
Изображения декодируются с ограничениями, текстуры кэшируются по содержимому.
Невыпуклые контуры тесселируются earcutr исключительно для отображения.

Базовые команды схемы находятся в `eda-core::schematic_edit`; Request проверяет
документ/ревизию, preview/commit используют одну проверяемую реализацию.
GUI хранит инструмент и черновик Properties в schematic_editor.rs;
eda-render возвращает ввод в координатах документа. Исходный native-архив
не меняется; `source_modified` отличает его от актуальной сцены. Контракт и
ограничения: docs/schematic-editing.md и ADR 0003.

Связность, DRC, трассировка и schematic compiler ещё не реализованы.
Типы выводов и метаданные импортированы, но инженерная семантика не проверяется. Pads/Tracks
в примере — собственные геометрические примитивы без nets/footprints.

Linux и Windows — равноправные целевые платформы. Пути хранятся в PathBuf,
файловый слой использует стандартный Rust API и tempfile; платформенные
диалоги предоставляет rfd. X11/Wayland включены явно. Настройка локального
GNU linker на Windows ограничена scripts/dev.ps1 и игнорируемым .tools.
Общая строка заголовка и оконные команды используют egui viewport API;
Win32 не добавлен в UI-код. Системные шрифты Windows читаются опционально;
Linux и fallback используют включённые в binary Selawik по OFL.
Properties вынесена в properties.rs, chrome — в chrome.rs, отрисовка
иконок/шрифты/общая тема — в theme.rs. Геометрический snapping остаётся
состоянием View в eda-render и не меняет координаты документа.
Проверки Linux и Windows заданы в .github/workflows/check.yml; визуальный
запуск на каждой ОС требует отдельной проверки.

Первоисточники API: [eframe 0.32.3](https://docs.rs/eframe/0.32.3/eframe/),
[egui_dock 0.17.0](https://docs.rs/egui_dock/0.17.0/egui_dock/).
